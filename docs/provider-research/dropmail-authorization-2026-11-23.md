## 4. Careful reading of the third-party developer invitation

The docs do not merely tolerate third-party apps; they actively address them:

- "Building an app that gives _its own users_ temporary addresses?" (S3) — names **browser extension, desktop/mobile app and website** as the addressees. SpectreMail's MV3 extension is literally in that list.
- "Let each user get their own token via OAuth instead of shipping one token inside your app" (S3) — the provider **discourages** a single shared token, which aligns with this repository's no-shared-secret rule.
- "Returns a `client_id`; there is no client secret. Register once and reuse it" (S4) — **dynamic client registration** with no confidential client credential; suitable in principle for a distributed client.

**What this does establish (INFERRED, labelled):** third-party integration is _contemplated and invited_ at the technical level. It would be wrong to treat the word "competitor" as if a prohibition had been found — no source in §2 contains a prohibition of competitive use, resale, or repackaging. `PROHIBITED` is therefore **not** supported.

**What this does not establish (the load-bearing point):** none of S1–S10 contains a grant of _legal permission_, a licence, an attribution rule, or a statement about competitive use. S3–S5 are in "OAuth for apps" and "Get a free API token" — operational guidance, not terms. The provider has **no Terms of Service document** at any of the 17 ToS/legal paths probed (S11–S12), the only policy document is a 2017 privacy template (S10), and the homepage links nothing else (S9, S14). GOAL §3 (`docs/GOAL.md:38`) explicitly warns that "A public or free API does **not** automatically authorize repackaging it as a competing temporary-email product," and line 44 says unresolved permission is **REVIEW REQUIRED, not PASS**. An invitation to build an app is not a licence to ship a competing product; treating inference as permission would override that policy. **So the extension stays `PERMISSION REQUIRED`, not `CLEARLY PERMITTED`.**

**Credential-delivery gate (unchanged, NOT VERIFIED):** the documented redirect allow-list is `https://`, `http://localhost` / `http://127.0.0.1`, or a private-use scheme such as `myapp://callback` (S5). `chrome-extension://` is **not listed**. Whether an MV3 extension can complete this flow (e.g. via a private-use scheme or an extension-origin redirect) is a browser/platform question that needs a probe plus provider confirmation. **Nothing in this report confirms it works.** No probe was run and no per-user credential was created.

**OpenSpec:** this report changes no requirement and does not relax `docs/PROVIDERS.md` or any spec. No proxy, no shared secret, no claimed integration.
